## 1. Overview & Objective

Pixel Office V2.4 introduces a truthful, presentational **Task Handoff Visualization Layer** built directly on top of the approved V2.3A Central Hall topology and deterministic staff movement engine (`office-route-graph.ts` and `staff-movement.ts`).

The core capability allows operators to observe genuine workflow stage transitions in the 2D workplace:
1. Real workflow stage completed by Staff A (e.g. Joko completing draft writing).
2. Real next stage / assignment becomes active for Staff B (e.g. Rina assigned to Editorial QA).
3. Observable canonical handoff event displayed via a subtle HUD toast/indicator.
4. Staff A stops work and returns to the Executive Lounge if their canonical state becomes idle.
5. Staff B travels through the Central Hall to their workstation (e.g. Review Desk).
6. Staff B arrives and begins the corresponding MC-9 job animation (e.g. `QA_REVIEW`).

## 2. The Critical Truthfulness Rule

```
NO CANONICAL HANDOFF EVIDENCE = NO HANDOFF VISUALIZATION
```

1. **A movement coincidence is NOT a handoff.** If Staff A walks past Staff B in the Central Hall, no handoff is inferred or displayed.
2. **Two staff working sequentially is NOT automatically a handoff.** Timing coincidence across disparate workflows (e.g., Joko stopped at 10:02 and Rina started at 10:03 on different articles) is strictly rejected.
3. **Task Identity is mandatory.** A handoff only qualifies if the **same canonical task/workflow/article identity** is shared between the previous stage/owner and the next stage/owner.
4. **Zero physical file fabrications.** No flying envelopes, floating paper animations, cartoon delivery packages, or magic beams are used. The handoff represents workflow ownership and stage progression, not a physical object transfer.

## 3. Qualification Invariants & Evidence Sources

A handoff observation is derived strictly from authoritative database tables and pipeline states:

| Canonical Evidence Source | Extracted Fields | Qualification Logic |
| :--- | :--- | :--- |
| `pipeline.tasks` (`d1:articles`) | `taskId`, `stage`, `status`, `lastUpdate`, `relatedArticleId` | Transition between pipeline stages (`writing` $\rightarrow$ `editorial_qa` $\rightarrow$ `scheduled` $\rightarrow$ `ingesting`). |
| `d1:media_jobs` | `relatedMediaJobId`, `status`, `targetSlot` | Task awaiting media attachment or media handoff to editorial review. |
| `snapshot_delta:pipeline_tasks` | Matching `curr.taskId === prev.taskId` with changed stage/status | Dynamic runtime delta observed across polling intervals. |

### Minimum Required Proof:
$$\text{Task Handoff} = \text{Shared Task/Workflow ID} + \text{From Stage} + \text{To Stage} + \text{From Owner} + \text{To Owner} + \text{Deterministic Timestamp}$$

If any element is missing or ambiguous, the system fails closed to `NO_HANDOFF`.

## 4. Deterministic Event Identity & Deduplication

To prevent duplicate animations and eliminate random state changes, every handoff is assigned a deterministic identity generated by an FNV-1a hash of its invariant attributes:

```typescript
export function deriveDeterministicHandoffId(
  workflowId: string,
  fromStage: string,
  toStage: string,
  fromAgent: string | null,
  toAgent: string | null,
  timestamp: string
): string
```

- **Zero UUIDs:** Random identifiers (`crypto.randomUUID()`) are strictly forbidden.
- **Idempotency:** 50 calls with identical arguments yield the exact same identifier (`hnd_<workflow>_<from>_to_<to>_<hex>`).
- **Consumed Sets:** The client runtime tracks `consumedHandoffIds = new Set()`. Once a handoff ID has been presented, repeated polling or page re-evaluations will never re-trigger animations.

## 5. State Semantics & Movement Interaction

A handoff can resolve to one of three operational states:

```
               ┌── RUNNING ──> Staff leaves Lounge -> Central Hall -> Workstation -> MC-9 Animation
               │
HANDOFF STATE ─┼── QUEUED  ──> Handoff observed in HUD/Toast -> Staff STAYS in Lounge (requires_movement = false)
               │
               └── BLOCKED ─> Handoff observed -> Staff marked with CRITICAL warning (zero fake active work)
```

1. **`RUNNING` Next Stage:**
   - `requires_movement = true`.
   - Destination staff member navigates from their idle lounge seat through the Central Hall to their department workstation.
   - Upon arrival, the docked sprite starts their MC-9 role animation.
2. **`QUEUED` Next Stage:**
   - `requires_movement = false`.
   - The HUD toast displays: `"Transferred to Publication Queue (Sari Standby in Lounge)"`.
   - The staff member **strictly remains stationary** in the Executive Lounge. No premature journey to the workstation is permitted.
   - When canonical state later shifts to `RUNNING`, movement is initiated.
3. **`BLOCKED` Next Stage:**
   - `requires_movement = false`.
   - Handoff status shows `BLOCKED` with critical warning indication. Zero fake active work or typing animation is executed.

---

## 6. Initial Load & Refresh Replay Prevention

1. **Initial Page Load:**
   - Historical handoffs are loaded into the `Recent Handoffs` panel and added to `consumedHandoffIds`.
   - Staff sprites are rendered directly at their current canonical workstations or lounge seats.
   - Historical travel sequences are **never replayed** as animations on initial load.
2. **Page Refresh:**
   - Polling identical snapshots generates an empty delta (`detectSnapshotDeltaHandoffs` returns `[]`).
   - Already consumed handoffs remain silent.
